# 个人财务管理系统需求规格说明

> 文件路径：`docs/requirements.md`  
> 文档版本：v1.0  
> 文档状态：需求基线  
> 适用范围：第一版（MVP）  
> 使用对象：单用户，仅系统所有者本人

---

## 1. 文档目的

本文档定义个人财务管理系统第一版的目标、系统边界、业务规则、功能需求、非功能需求与验收标准。

本文档将作为后续系统设计、Codex 任务规划、编码、测试和部署的主要输入。第一版以“实际可用、逻辑正确、部署简单、维护成本低”为目标，不追求企业级流程或过度工程化。

---

## 2. 项目背景

系统所有者是一名暂无稳定收入的大学生，主要资金来源为父母提供的生活费，并计划办理人生中的第一张信用卡。

系统需要帮助用户：

1. 准确记录个人收入、支出、账户转账、信用卡消费和还款；
2. 控制月度预算和非必要消费；
3. 确保信用卡账单能够按期全额偿还；
4. 管理商品分期产生的未来付款义务；
5. 通过支付宝、微信账单文件降低手工记账成本；
6. 在不绑定真实支付账号的前提下保护个人财务数据；
7. 通过低成本云端部署实现随时访问。

---

## 3. 项目目标

### 3.1 核心目标

系统应当能够快速回答以下问题：

- 当前流动资产有多少；
- 当前信用卡已出账、未出账和总负债分别是多少；
- 下一还款日及本期尚需偿还多少；
- 不动用储备资金时能否全额还款；
- 动用储备资金后能否全额还款；
- 本月预算已经使用多少、还剩多少；
- 各分类支出是否接近或超过预算；
- 当前分期在未来各月占用多少预算；
- 新增分期后，未来月份是否存在资金缺口；
- 本月收入、支出、储蓄目标和净资金变化情况如何。

### 3.2 成功标准

第一版成功交付应至少满足：

1. 用户可以在电脑浏览器中完成主要操作；
2. 账户余额、交易统计、信用卡还款和分期预算不存在重复计算；
3. 支持支付宝和微信账单文件导入，并在确认后进入正式账本；
4. 支持预算、风险预警和未来偿还能力预测；
5. 支持完整备份、恢复和 CSV 导出；
6. 可以通过 Docker Compose 部署到低配置 Linux 云服务器；
7. 系统通过 HTTPS 访问，未登录用户无法读取财务数据。

---

## 4. 项目范围与边界

### 4.1 第一版范围

第一版包含：

- 单用户登录；
- 资产账户和一张信用卡管理；
- 手动交易录入；
- 支付宝、微信账单文件导入；
- 收入、支出、转账、退款和余额调整；
- 信用卡账单与全额还款管理；
- 商品分期管理；
- 月度总预算和分类预算；
- 固定支出、预计收入和储蓄目标；
- 风险预警和未来现金流预测；
- 仪表盘和统计报表；
- CSV 导出、JSON 完整备份与恢复；
- 云端部署与自动数据库备份。

### 4.2 不在第一版范围内

第一版不实现：

- 支付宝、微信个人账单 API 自动同步；
- 模拟登录、抓取支付应用内部接口或保存支付平台凭证；
- 银行卡和信用卡自动同步；
- 手机原生应用；
- 完整离线使用和多端同步；
- 多用户、角色和权限管理；
- AI 自动分类；
- 邮件、短信、微信和手机推送提醒；
- 双因素认证；
- 投资、基金、股票和多币种管理；
- 发票与报销管理；
- 企业级高可用、集群、负载均衡和 Kubernetes。

### 4.3 终端与部署边界

- 主要终端：电脑浏览器；
- 手机端：仅保证基础访问，可作为账单文件或其他数据来源；
- 部署方式：低成本 Linux 云服务器；
- 第一版不要求离线使用；
- 系统仅记录和分析财务数据，不发起任何真实支付或转账。

---

## 5. 用户与权限

### 5.1 用户模型

系统仅存在一个管理员用户。

系统不得提供：

- 公开注册；
- 多用户切换；
- 第三方登录；
- 邮箱或手机号绑定；
- 支付宝、微信、银行账号授权。

### 5.2 登录凭证

系统使用独立密码。该密码不得与支付宝、微信、邮箱、银行卡等真实账号密码复用。

## 6. 核心术语

| 术语 | 定义 |
|---|---|
| 流动资产 | 银行卡余额、微信余额和支付宝余额之和 |
| 当前信用卡负债 | 已出账未还金额与未出账金额之和 |
| 当前净资金 | 流动资产减去当前信用卡负债 |
| 已出账 | 已进入最近一期信用卡正式账单的金额 |
| 未出账 | 已发生但尚未进入最近一期正式账单的金额 |
| 账单日 | 银行汇总一个账期交易并生成账单的日期 |
| 还款日 | 必须全额偿还本期应还金额的最后日期 |
| 储蓄目标 | 本月计划新增并保留的资金，默认值为 0 |
| 累计储备资金 | 过去月份已积累、用于风险缓冲的资金 |
| 分期计划 | 附属于一笔消费的未来付款安排，不是独立交易类型 |
| 长期消费承诺 | 分期消费尚未支付的未来总金额 |
| 预计收入 | 尚未到账的未来收入，不直接改变当前账户余额 |
| 确定收入 | 可靠性足够高、可参与未来偿还能力预测的预计收入 |
| 支付渠道 | 支付宝、微信等交易发生的平台 |
| 实际账户 | 实际发生资金增减的银行卡、微信余额、支付宝余额或信用卡 |

## 7. 核心业务规则

### 7.1 信用卡规则

**BR-001** 系统只管理一张信用卡。

**BR-002** 信用卡账单必须全额还款，系统不支持最低还款作为正常完成状态。

**BR-003** 系统不得提供信用卡账单分期操作。

**BR-004** 系统允许在购买商品时建立商品分期计划，包括免息分期和明确手续费的分期。

**BR-005** 信用卡额度不计入资产。

**BR-006** 信用卡消费发生后立即增加信用卡负债，不得等到账单生成后才计入。

**BR-007** 信用卡还款属于账户间资金转移，不得再次计入消费支出。

### 7.2 账户规则

**BR-008** 第一版默认管理以下账户：

- 银行卡；
- 微信余额；
- 支付宝余额；
- 信用卡。

**BR-009** 第一版不记录现金账户。

**BR-010** 不建立校园卡账户。校园卡充值直接记录为“餐饮”支出，充值后在校园卡内的具体消费不再记录。

**BR-011** 自有账户之间的资金转移不属于收入或支出。

**BR-012** 有历史交易的账户不得直接删除，只能停用。

### 7.3 交易规则

系统底层仅保留以下五类交易：

| 类型 | 定义 |
|---|---|
| 收入 | 外部资金进入资产账户 |
| 支出 | 使用资产账户或信用卡发生消费 |
| 转账 | 自有账户之间转移资金，包括信用卡还款 |
| 退款 | 全部或部分冲销原始支出 |
| 余额调整 | 修正系统余额与实际余额之间的差异 |

**BR-013** “信用卡消费”是以信用卡为实际账户的支出，不是新的底层交易类型。

**BR-014** “信用卡还款”是资产账户向信用卡账户的转账，不是支出。

**BR-015** “分期”附属于原始消费，不是独立交易类型。

**BR-016** “手续费”计入实际每期还款金额，第一版不要求单独拆分统计。

**BR-017** 退款必须尽量关联原始支出，并冲减原分类支出和预算占用。

**BR-018** 余额调整不得进入正常收入、支出和预算统计。

### 7.4 分期规则

**BR-019** 分期消费必须记录：

- 商品名称；
- 商品原价；
- 分类；
- 购买日期；
- 分期期数；
- 每期实际还款金额；
- 首期月份；
- 分期来源；
- 当前状态。

**BR-020** 每期实际还款金额已经包含手续费时，系统直接按该金额占用预算。

**BR-021** 分期商品原价不一次性占用购买当月预算。

**BR-022** 每一期实际应付金额占用对应月份的分类预算和总预算。

**BR-023** 商品总价和剩余分期金额应作为长期消费承诺单独展示。

**BR-024** 分期计划创建后，应自动预占未来各月预算。

**BR-025** 分期还款不应与信用卡还款重复计入支出。

**BR-026** 提前结清时由用户录入实际结清金额和日期，系统取消后续计划并以实际账单为准。

**BR-027** 分期退款由用户关联原消费，并根据实际账单手动调整剩余期数和金额。

### 7.5 预算规则

**BR-028** 预算以自然月为单位。

**BR-029** 第一版支持：

- 月度总支出预算；
- 分类预算；
- 固定支出；
- 分期预算占用；
- 储蓄目标；
- 最低安全余量。

**BR-030** 储蓄目标默认值为 0。

**BR-031** 储蓄目标占用本月可分配预算，但不属于消费支出。

**BR-032** 每月可自由分配预算按以下口径计算：

```text
本月可自由分配预算
= 本月总支出预算
- 固定支出
- 当月分期
- 本月储蓄目标
```

**BR-033** 分类预算和分类名称必须可调整。

**BR-034** 已被历史交易使用的分类不得直接删除，只能停用。

**BR-035** 第一版使用扁平分类，不实现父子分类。

### 7.6 储备资金规则

**BR-036** 累计储备资金用于风险缓冲，不是永久不可使用资金。

**BR-037** 系统同时计算常规偿还能力和最终偿还能力。

```text
常规可还款资金
= 流动资产
- 还款日前必须支付的必要支出
- 当前计划保留的储备资金
```

```text
最终可还款资金
= 流动资产
- 还款日前必须支付的必要支出
```

**BR-038** 信用卡还款风险分为：

| 状态 | 条件 |
|---|---|
| 安全 | 常规可还款资金足以全额偿还本期账单 |
| 需要动用储备 | 常规资金不足，但最终可还款资金足够 |
| 危险 | 动用可用储备后仍不足以全额偿还 |

### 7.7 未来偿还能力规则

**BR-039** 未来偿还能力按月预测。

**BR-040** 只有“确定收入”参与偿还能力预测；较可能收入和不确定收入只作参考。

**BR-041** 未来月份预测至少考虑：

- 月初预计可用资金；
- 确定预计收入；
- 必要支出预算；
- 固定支出；
- 已有分期；
- 新增分期；
- 储蓄目标；
- 最低安全余量。

**BR-042** 新增分期后的状态分为：

| 状态 | 含义 |
|---|---|
| 安全 | 完成储蓄目标后仍无资金缺口 |
| 可承担 | 需要降低或暂停储蓄目标，但仍可还款 |
| 需要动用储备 | 常规资金不足，但储备资金可以覆盖 |
| 高风险 | 即使暂停储蓄并动用可用储备，仍存在资金缺口 |

**BR-043** 系统仅提供预警，不强制阻止用户录入消费。

**BR-044** 不要求现有流动资产覆盖全部未来分期剩余金额。

## 8. 默认分类

### 8.1 必要消费

- 餐饮；
- 交通；
- 日用品；
- 通信；
- 学习；
- 医疗；
- 固定订阅。

### 8.2 弹性消费

- 娱乐；
- 社交；
- 服饰；
- 数码产品；
- 旅行；
- 其他。

### 8.3 分类管理要求

用户必须能够：

- 新增分类；
- 修改分类名称；
- 设置分类为必要消费或弹性消费；
- 设置默认预算；
- 调整显示顺序；
- 停用分类；
- 修改历史交易所属分类。

“冲动消费”作为交易标签，而不是用途分类。

## 9. 功能需求

## 9.1 登录与会话

**FR-AUTH-001** 系统应提供单用户登录页。

**FR-AUTH-002** 系统不得提供注册功能。

**FR-AUTH-003** 登录失败达到限制后应临时阻止继续尝试。

默认规则：15 分钟内最多失败 5 次。

**FR-AUTH-004** 系统应支持主动注销。

**FR-AUTH-005** 系统应在长时间无操作后自动退出。

默认无操作时长：60 分钟；默认会话最长时间：24 小时。

**FR-AUTH-006** 用户应能够修改系统密码。

## 9.2 账户管理

**FR-ACC-001** 系统应默认创建银行卡、微信余额、支付宝余额和信用卡四类账户。

**FR-ACC-002** 用户应能够修改账户名称、初始余额、实际余额、启用状态和显示顺序。

**FR-ACC-003** 系统应显示每个资产账户的：

- 系统计算余额；
- 用户录入的实际余额；
- 余额差异。

**FR-ACC-004** 用户应能够通过余额调整修正差异。

**FR-ACC-005** 有历史交易的账户只能停用，不能直接删除。

## 9.3 手动记账

**FR-TXN-001** 系统应提供以下操作入口：

- 记录收入；
- 记录普通支出；
- 记录信用卡消费；
- 账户间转账；
- 信用卡还款；
- 记录退款；
- 余额调整。

**FR-TXN-002** 普通交易至少应记录：

- 金额；
- 日期和时间；
- 分类；
- 支付渠道；
- 实际账户；
- 商家或交易对象；
- 备注；
- 可选标签。

**FR-TXN-003** 系统应支持新增、编辑、作废或删除错误交易。

**FR-TXN-004** 删除存在关联关系的交易前，系统必须提示影响并阻止破坏性删除。

**FR-TXN-005** 系统应支持按时间、类型、账户、分类、金额和关键词筛选交易。

**FR-TXN-006** 系统应支持复制历史交易。

**FR-TXN-007** 系统应记住常用或最近使用的账户，并允许建立常用交易模板。

## 9.4 退款与余额调整

**FR-REF-001** 退款应支持全额退款和部分退款。

**FR-REF-002** 退款应关联原始支出；无法自动关联时由用户选择。

**FR-REF-003** 普通退款应冲减原分类支出和预算占用。

**FR-REF-004** 分期退款应允许用户手动调整未来分期计划。

**FR-ADJ-001** 余额调整应记录金额、账户、日期和原因。

**FR-ADJ-002** 余额调整不得计入普通收入、支出或预算。

## 9.5 信用卡管理

**FR-CC-001** 系统应允许设置：

- 信用额度；
- 个人月度信用卡消费上限；
- 账单日；
- 还款日。

**FR-CC-002** 系统应显示：

- 已出账金额；
- 未出账金额；
- 当前信用卡总负债；
- 本期已还金额；
- 本期剩余应还金额；
- 下一还款日。

**FR-CC-003** 系统应支持按账期查看交易和还款状态。

账期状态包括：

- 未出账；
- 待还款；
- 部分还款；
- 已全额还款；
- 已逾期。

**FR-CC-004** 系统不得将“最低还款完成”视为完成状态。

**FR-CC-005** 信用卡还款应选择资金来源账户，并作为转账处理。

**FR-CC-006** 系统应分别显示常规偿还能力、最终偿还能力和对应风险状态。

## 9.6 分期管理

**FR-INS-001** 用户应能够为消费创建分期计划。

**FR-INS-002** 分期计划至少包含：

- 商品名称；
- 商品原价；
- 分类；
- 分期期数；
- 每期实际金额；
- 首期月份；
- 分期来源；
- 当前状态；
- 备注。

**FR-INS-003** 系统应自动计算：

- 总还款金额；
- 剩余期数；
- 剩余应付金额；
- 未来各月应付金额。

**FR-INS-004** 每期金额应自动占用对应月份分类预算和总预算。

**FR-INS-005** 系统应单独展示本月新增分期商品总额和剩余长期消费承诺。

**FR-INS-006** 系统应支持以下状态：

- 进行中；
- 已完成；
- 提前结清；
- 已取消；
- 退款处理中。

**FR-INS-007** 用户应能够录入提前结清实际金额和日期。

**FR-INS-008** 用户应能够根据实际账单手动调整剩余期次和每期金额。

## 9.7 预算管理

**FR-BUD-001** 用户应能够为每个月设置总支出预算、储蓄目标和最低安全余量。

**FR-BUD-002** 用户应能够为每个支出分类设置月度预算。

**FR-BUD-003** 系统应分别显示：

- 普通支出；
- 固定支出；
- 分期占用；
- 总占用；
- 剩余预算；
- 使用比例。

**FR-BUD-004** 用户应能够从上月复制预算。

**FR-BUD-005** 用户应能够查看未来月份被分期预占的预算。

**FR-BUD-006** 用户应能够临时调整储蓄目标。

**FR-BUD-007** 分类预算达到默认 80% 时应提醒，达到 100% 时应警告。

阈值应可配置。

## 9.8 固定支出与预计收入

**FR-PLAN-001** 用户应能够创建固定支出计划，包括名称、金额、分类、发生周期、预计日期和启用状态。

**FR-PLAN-002** 固定支出示例包括：

- 手机套餐；
- 软件或会员订阅；
- 云服务器费用；
- 固定学习服务；
- 固定交通费用。

**FR-PLAN-003** 用户应能够创建预计收入，包括名称、金额、预计到账日期、周期和可靠程度。

可靠程度包括：

- 确定；
- 较可能；
- 不确定。

**FR-PLAN-004** 预计收入在实际到账前不得改变账户余额或本月实际收入。

**FR-PLAN-005** 预计收入到账后应能够转换或关联为正式收入记录。

## 9.9 账单文件导入

**FR-IMP-001** 第一版应支持支付宝和微信账单文件导入。

**FR-IMP-002** 账单导入流程必须为：

```text
上传文件
→ 识别来源
→ 解析
→ 账户映射
→ 分类推荐
→ 重复检测
→ 用户确认
→ 正式导入
```

**FR-IMP-003** 导入记录必须先进入待确认区，不得直接写入正式账本。

**FR-IMP-004** 导入记录状态包括：

- 待确认；
- 已忽略；
- 已导入；
- 疑似重复；
- 解析失败。

**FR-IMP-005** 系统应区分支付渠道和实际支付账户。

**FR-IMP-006** 无法识别实际账户时，用户应能够手动选择。

**FR-IMP-007** 系统应优先使用稳定流水号精确去重。

**FR-IMP-008** 无稳定流水号时，应根据以下特征提示疑似重复：

- 交易时间接近；
- 金额相同；
- 商家相似；
- 实际账户相同；
- 交易方向相同。

**FR-IMP-009** 疑似重复记录不得自动删除，用户可选择：

- 保留手动记录；
- 使用导入记录替换；
- 两条都保留；
- 合并信息。

**FR-IMP-010** 用户应能够批量修改分类、实际账户、确认导入或忽略记录。

**FR-IMP-011** 系统应使用可扩展账单解析器设计，以便后续增加银行卡和信用卡账单解析器。

## 9.10 自动分类规则

**FR-CAT-001** 系统应通过商家关键词规则推荐分类，不要求使用 AI。

**FR-CAT-002** 用户修改分类后，可以保存“相同商家以后自动归类”的规则。

**FR-CAT-003** 用户应能够新增、编辑、停用和调整规则优先级。

## 9.11 仪表盘

**FR-DASH-001** 首页应展示：

- 流动资产；
- 当前信用卡负债；
- 当前净资金；
- 本月实际收入；
- 本月预算占用；
- 本月剩余预算；
- 累计储备资金；
- 下一还款日和本期剩余应还金额。

**FR-DASH-002** 首页应展示以下风险状态：

- 信用卡还款状态；
- 本月预算状态；
- 未来分期状态。

**FR-DASH-003** 首页应展示未来 30 天内的：

- 信用卡还款；
- 分期应付款；
- 固定支出；
- 确定预计收入；
- 预算预警。

**FR-DASH-004** 首页应提供快捷操作：

- 记收入；
- 记支出；
- 记信用卡消费；
- 信用卡还款；
- 导入账单。

## 9.12 风险预警

**FR-RISK-001** 系统应支持以下预警：

| 预警 | 默认条件 |
|---|---|
| 分类预算提醒 | 使用达到 80% |
| 分类预算超支 | 使用达到 100% |
| 信用卡还款提醒 | 距还款日 7、3、1 天 |
| 信用卡还款风险 | 常规或最终可还款资金不足 |
| 分期风险 | 任一未来月份预计出现资金缺口 |
| 大额消费提醒 | 单笔弹性消费超过自定义阈值 |
| 信用卡个人上限 | 当月信用卡消费达到个人设定上限 |

**FR-RISK-002** 预警阈值应可配置。

**FR-RISK-003** 第一版预警仅在系统内部展示，不要求外部推送。

## 9.13 统计报表

**FR-REP-001** 系统应提供月度收支趋势。

**FR-REP-002** 系统应提供分类支出统计。

**FR-REP-003** 系统应提供每日支出趋势。

**FR-REP-004** 系统应提供预算执行情况。

**FR-REP-005** 系统应提供信用卡使用情况。

**FR-REP-006** 系统应提供分期负担情况。

**FR-REP-007** 系统应提供储蓄目标完成情况。

**FR-REP-008** 首页和报表应允许切换统计月份。

## 10. 统计口径

| 操作 | 计入收入 | 计入预算支出 | 影响账户余额 |
|---|---:|---:|---:|
| 外部资金转入 | 是 | 否 | 是 |
| 普通消费 | 否 | 是 | 是 |
| 自有账户转账 | 否 | 否 | 是 |
| 信用卡普通消费 | 否 | 是 | 是，增加负债 |
| 信用卡还款 | 否 | 否 | 是 |
| 分期商品当期金额 | 否 | 是 | 是，进入相应账期 |
| 分期剩余金额 | 否 | 否 | 否，仅作为未来承诺 |
| 普通退款 | 否 | 冲减原支出 | 是 |
| 余额调整 | 否 | 否 | 是 |
| 预计收入 | 否 | 否 | 否 |
| 储蓄目标 | 否 | 占用预算但不算消费 | 否 |

系统默认采用现金流管理口径：

```text
消费支出
= 普通支出
+ 信用卡普通消费
+ 当期分期金额
- 退款
```

```text
预算占用
= 消费支出
+ 储蓄目标
```

信用卡还款不得再次计入消费。

## 12. 非功能需求

## 12.1 安全性

**NFR-SEC-001** 所有生产环境访问必须使用 HTTPS。

**NFR-SEC-002** HTTP 应自动跳转 HTTPS。

**NFR-SEC-003** 数据库端口不得向公网开放。

**NFR-SEC-004** 未登录用户不得访问财务页面和 API。

**NFR-SEC-005** 密码必须使用可靠的密码哈希算法存储，不得明文保存。

**NFR-SEC-006** Cookie 应启用 HTTPS 限制，并禁止前端脚本读取。

**NFR-SEC-007** 代码仓库中不得包含生产密码、密钥或会话秘密。

**NFR-SEC-008** 系统不得保存：

- 完整银行卡号；
- 信用卡安全码；
- 支付密码；
- 短信验证码；
- 支付平台登录凭证；
- 身份证信息。

**NFR-SEC-009** 导入文件中的账号、卡号等敏感字段在保存前应删除或脱敏。

## 12.2 文件安全

**NFR-FILE-001** 原始账单文件不得存放在公开目录。

**NFR-FILE-002** 原始账单文件应在完成处理后及时删除，最迟不得超过 24 小时。

**NFR-FILE-003** 系统应限制上传文件类型和大小。

**NFR-FILE-004** 日志不得输出原始账单内容。

## 12.3 日志

日志可以记录：

- 登录成功和失败；
- 接口异常；
- 导入任务结果；
- 备份结果；
- 系统启动和关闭。

日志不得记录：

- 密码；
- Cookie 或会话令牌；
- 完整交易备注；
- 完整账户标识；
- 完整账单内容。

## 12.4 数据完整性

**NFR-DATA-001** 所有金额必须使用精确十进制类型，精确到人民币分。

**NFR-DATA-002** 以下操作必须在数据库事务中整体成功或整体失败：

- 转账；
- 信用卡还款；
- 批量确认导入；
- 创建消费及分期计划；
- 退款及原交易冲减；
- 数据恢复。

**NFR-DATA-003** 存在关联关系的数据不得被直接破坏性删除。

## 12.5 性能与资源

系统面向单用户、低并发场景。

目标运行环境：

- 1 核 CPU；
- 1GB～2GB 内存；
- 少量磁盘空间；
- 单机数据库。

第一版不要求复杂性能优化，但常用页面和查询在正常数据规模下应保持可接受响应速度。

## 12.6 可用性

- 桌面端优先；
- 手机端保证基础访问；
- 表单应提供合理默认值；
- 常用操作应在少量步骤内完成；
- 页面应明确区分收入、支出、转账和还款，避免用户误记。

## 12.7 时间与时区

- 数据库存储采用统一时间基准；
- 页面按系统配置时区展示；
- 时区可修改；
- 账单日、还款日和月度统计不得因服务器时区产生日期偏差。

## 13. 备份与恢复

### 13.1 自动数据库备份

系统每天自动备份数据库。

默认保留策略：

- 最近 7 份每日备份；
- 最近 4 份每周备份。

### 13.2 完整备份

系统应支持 JSON 完整导出，至少包含：

- 账户；
- 交易；
- 分类；
- 预算；
- 信用卡账期；
- 还款记录；
- 分期计划；
- 固定支出；
- 预计收入；
- 分类规则；
- 系统配置。

### 13.3 CSV 导出

系统应支持将交易和主要统计数据导出为 CSV。

CSV 用于查看和分析，不承担完整恢复功能。

### 13.4 恢复要求

系统应支持从完整 JSON 备份恢复。

恢复前必须：

1. 校验文件格式和版本；
2. 自动备份当前数据；
3. 在事务中执行恢复；
4. 恢复失败时保持原数据不变。

用户应能够定期将完整备份下载到本地电脑，作为异地备份。

## 15. 验收标准

## 15.1 登录与安全

- 未登录用户无法访问财务页面和 API；
- 连续错误登录会触发限制；
- HTTP 自动跳转 HTTPS；
- 数据库不能从公网直接访问；
- 仓库中不包含生产密码或密钥；
- 修改密码和注销功能有效。

## 15.2 账户与交易

- 能管理银行卡、微信余额、支付宝余额和一张信用卡；
- 能录入初始余额和实际余额；
- 能显示系统余额与实际余额差异；
- 能正确处理收入、支出、转账、信用卡消费、信用卡还款、退款和余额调整；
- 转账不计入收入或支出；
- 信用卡还款不重复计入消费；
- 退款正确冲减原支出；
- 余额调整不进入普通收支统计。

## 15.3 信用卡

- 能设置账单日和还款日；
- 能区分已出账和未出账；
- 能记录信用卡还款；
- 能判断本期账单是否全额还清；
- 不提供最低还款或账单分期操作；
- 能显示常规偿还能力、最终偿还能力及风险状态。

## 15.4 分期

- 能创建商品分期；
- 能设置商品原价、期数、每期金额和首期月份；
- 每期金额正确占用对应月份预算；
- 商品总价作为长期消费承诺展示；
- 能查看未来月份分期占用；
- 能处理提前结清和退款调整；
- 分期还款不与信用卡还款重复计入支出。

## 15.5 预算与风险

- 支持月度总预算、分类预算、固定支出、储蓄目标和最低安全余量；
- 支持从上月复制预算；
- 正确显示普通支出、固定支出、分期占用和剩余预算；
- 预算达到 80% 和 100% 时正确预警；
- 创建或修改分期后能预测未来月份；
- 能区分安全、可承担、需要动用储备和高风险；
- 风险预警不会阻止用户继续录入。

## 15.6 账单导入

- 能上传并解析支持的支付宝和微信账单文件；
- 解析结果先进入待确认区；
- 支持账户映射、分类修改和批量确认；
- 能通过流水号或特征识别疑似重复；
- 疑似重复由用户决定处理方式；
- 原始文件及时删除；
- 导入失败不污染正式账本；
- 重复导入不会造成大量重复交易。

## 15.7 报表

系统能够正确展示：

- 月度收入与支出；
- 分类支出；
- 每日支出趋势；
- 预算执行情况；
- 当前净资金变化；
- 信用卡使用情况；
- 分期负担情况；
- 储蓄目标完成情况。

## 15.8 备份与部署

- 能生成完整 JSON 备份；
- 能从完整备份恢复；
- 能导出 CSV；
- 至少完成一次“备份—清空测试环境—恢复—核对”的测试；
- 能通过 Docker Compose 部署；
- 云端可以通过 HTTPS 访问；
- 服务器重启后服务可以自动启动。

## 18. 需求变更原则

由于系统为个人自用项目，后续允许轻量迭代。

需求变更应遵循：

1. 优先保证账务计算正确；
2. 不破坏已有数据；
3. 不引入真实支付账号安全风险；
4. 不为了形式完整而增加明显无用的复杂度；
5. 新需求先记录到文档，再决定是否进入当前开发周期；
6. 涉及交易统计口径、信用卡负债或分期逻辑的修改必须补充测试。
